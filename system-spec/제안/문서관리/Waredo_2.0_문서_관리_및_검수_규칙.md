# Waredo 2.0 — 문서 관리 및 검수 규칙

> 결정 상태: `[제안]` · 검수 상태: `[초안]`
>
> 문서 목적: 프로젝트 문서의 작성, 검수, 승인, 변경 및 Git 기록 기준을 통일한다.
>
> 적용 범위: GDD, 시스템 기획서, 콘텐츠 기획서, 기술 문서, 디자인 명세 및 회의 결정 기록

## 1. 기본 원칙

1. **확정된 사실과 제안을 분리한다.** 확정되지 않은 내용은 확정형 문장으로 작성하지 않는다.
2. **하나의 내용에는 하나의 기준 문서만 둔다.** 동일한 규칙을 여러 문서에서 각각 정의하지 않는다.
3. **변경 이유를 남긴다.** 결과만 수정하지 않고 변경 배경과 영향 범위를 기록한다.
4. **검수 전 문서를 구현 기준으로 사용하지 않는다.** 초안과 검수 중 문서는 참고 자료로만 사용한다.
5. **관련 시스템과의 충돌을 확인한다.** 개별 문서가 자연스러워도 상위 GDD 및 다른 시스템과 모순되면 확정하지 않는다.
6. **사용자가 제공하지 않은 규칙과 수치를 임의로 확정하지 않는다.** 부족한 내용은 지정 표기로 남긴다.

## 2. 문서 상태

모든 관리 대상 문서는 `결정 상태`와 `검수 상태`를 분리해 표시한다.

### 2.1 결정 상태

| 상태 | 의미 | 저장 위치 | 사용 가능 범위 |
|---|---|---|---|
| `[제안]` | 검토·검수·논의 중이며 최종 결정되지 않음 | `제안/` | 참고 및 검수 가능, 공식 구현 기준 사용 불가 |
| `[확정]` | 책임자 또는 회의의 최종 결정을 완료함 | `확정/` | 프로젝트 공식 기준으로 사용 가능 |

검수를 통과했더라도 최종 결정 전에는 `[제안]` 상태를 유지한다. `[확정]`으로 변경할 때 문서를 `제안/`에서 대응하는 `확정/` 하위 폴더로 이동한다.

### 2.2 검수 상태

| 상태 | 의미 |
|---|---|
| `[아이디어]` | 방향을 탐색하는 초기 메모 |
| `[초안]` | 기본 구조를 작성했으나 자체 검수가 끝나지 않음 |
| `[검수 요청]` | 자체 검수를 완료하고 팀 검수를 요청함 |
| `[수정 필요]` | 검수에서 해결해야 할 문제가 발견됨 |
| `[검수 완료]` | 필수 검수 사항을 해결하고 최종 결정 대기 중 |

결정 상태, 검수 상태와 본문 표기는 서로 다른 목적으로 사용한다.

- 결정 상태: 문서 전체가 제안인지 공식 확정안인지 표시
- 검수 상태: 문서 작성과 검토 진행 단계 표시
- `[유지]`, `[변경]`, `[신규]`, `[고도화]`: 시스템 변경 성격
- `[제안]`, `[논의 필요]`, `[작성 필요]`, `[회의 후 결정]`: 개별 항목의 결정 상태
- `[추후 기획]`, `[추후 구현]`: 현재 범위에서 제외된 후속 작업

`[확정]` 문서 안에도 `[작성 필요]`가 남을 수 있다. 이 경우 해당 미작성 항목은 확정 범위에서 제외된 것으로 본다.

## 3. 문서 상단 필수 정보

모든 신규 문서는 가능한 범위에서 다음 정보를 기록한다.

```markdown
> 결정 상태: [제안]
> 검수 상태: [초안]
> 문서 책임자: [작성 필요]
> 검수자: [작성 필요]
> 최초 작성일: YYYY-MM-DD
> 최근 수정일: YYYY-MM-DD
> 기준 문서: [문서명 또는 없음]
> 관련 문서: [문서명 또는 없음]
> 확정 범위: [작성 필요]
```

책임자와 검수자가 같은 경우에도 자체 검수와 승인 검수를 구분해 기록한다.

## 4. 기준 문서 관리

### 4.1 기준 문서

- 프로젝트 전체 규칙의 최종 기준은 메인 GDD로 관리한다.
- 신규 시스템은 검수 전까지 별도 문서에서 작성할 수 있다.
- 별도 시스템 문서의 검수가 완료되거나 `[확정]`되면 메인 GDD 반영 여부와 위치를 결정한다.
- 메인 GDD와 별도 문서가 충돌하면 임의로 한쪽을 선택하지 않고 `[논의 필요]`로 기록한다.
- 메인 GDD에 반영한 뒤 별도 문서를 유지한다면, 어느 문서가 원본인지 상단에 명시한다.

### 4.2 중복 방지

동일한 내용을 여러 문서에서 사용할 때는 다음 기준을 적용한다.

- 규칙 원문은 기준 문서 한 곳에만 작성한다.
- 다른 문서에서는 기준 문서와 항목을 참조한다.
- 요약이 필요한 경우 `요약`임을 표시하고 원문을 수정하지 않는다.
- 복사된 내용이 기준 문서와 달라지면 기준 문서의 내용을 우선한다.

## 5. 문서 작성 흐름

```text
아이디어 등록
→ 초안 작성
→ 작성자 자체 검수
→ 검수 요청
→ 팀 검수
→ 수정 또는 검수 완료
→ 필요 시 회의 결정
→ 확정
→ `제안/`에서 `확정/`으로 이동
→ 메인 GDD 및 관련 문서 반영
→ Git 커밋
```

### 5.1 아이디어 및 초안

- 검토되지 않은 방향은 `[아이디어]` 또는 `[제안]`으로 기록한다.
- 여러 선택지가 있으면 하나를 임의로 확정하지 않고 비교 기준과 `[논의 필요]` 항목을 작성한다.
- 수치, 예외, 우선순위가 정해지지 않았으면 `[작성 필요]`로 남긴다.

### 5.2 검수 요청

검수 요청 전 작성자는 자체 검수 체크리스트를 확인한다.

- 문서의 목적과 범위가 명확한가?
- 기존 GDD의 유지·변경·고도화 방향과 충돌하지 않는가?
- 용어가 기존 문서와 동일한 의미로 사용됐는가?
- 시스템의 진입, 실행, 종료 조건이 구분됐는가?
- 변수의 생성·변경 주체와 갱신 시점이 명확한가?
- 다른 시스템과의 입력·출력 관계가 빠지지 않았는가?
- 예외와 실패 상황이 누락되지 않았는가?
- 미정 내용을 확정형 문장으로 작성하지 않았는가?
- `[작성 필요]`, `[논의 필요]`, `[회의 후 결정]` 항목이 별도로 식별되는가?
- 개발·UI·아트·콘텐츠 등 영향받는 팀이 표시됐는가?

모든 항목을 통과하면 검수 상태를 `[검수 요청]`으로 변경한다.

## 6. 검수 규칙

검수는 다음 순서로 진행한다.

### 6.1 1차 — 구조 검수

- 문서 목적과 적용 범위가 분명한지 확인한다.
- 상위·하위 시스템 및 기준 문서를 확인한다.
- 중복 정의와 누락된 연결점을 확인한다.
- 결정 상태, 검수 상태와 항목별 상태 표기가 적절한지 확인한다.

### 6.2 2차 — 규칙 검수

- 동일한 조건에서 결과가 하나로 결정되는지 확인한다.
- 실행 순서, 갱신 시점, 우선순위가 충돌하지 않는지 확인한다.
- 정상 흐름뿐 아니라 취소·실패·중단·중복 발동 상황을 확인한다.
- 시스템이 소유하지 않은 값을 임의로 변경하지 않는지 확인한다.

### 6.3 3차 — 플레이 검수

- 플레이어가 무엇을 보고 어떤 판단을 하는지 설명 가능한지 확인한다.
- 선택지 사이에 실제 의미 있는 차이가 있는지 확인한다.
- 항상 정답인 선택이나 사용되지 않는 선택이 생기지 않는지 확인한다.
- 결과와 실패 원인을 UI 및 연출로 이해할 수 있는지 확인한다.
- 핵심 재미와 직접 연결되지 않는 복잡성이 과도하지 않은지 확인한다.

### 6.4 4차 — 제작 검수

- 프로그래밍에 필요한 규칙과 데이터가 정의됐는지 확인한다.
- UI에 표시할 정보와 상태가 정의됐는지 확인한다.
- 아트·애니메이션·이펙트 제작 범위가 구분됐는지 확인한다.
- 콘텐츠 제작에 필요한 공통 문법과 변수가 확정됐는지 확인한다.
- 선행 시스템이 확정되기 전에 하위 콘텐츠 제작을 요구하지 않는지 확인한다.

## 7. 검수 결과 기록

검수 의견은 다음 중 하나로 분류한다.

| 등급 | 의미 | 처리 기준 |
|---|---|---|
| `필수 수정` | 모순, 구현 불가, 핵심 규칙 누락, 확정 내용 충돌 | 검수 완료 전 반드시 해결 |
| `논의 필요` | 선택에 따라 시스템 방향이 달라짐 | 책임자 또는 회의 결정 필요 |
| `보완 권장` | 이해도·가독성·완성도를 높이는 개선 | 반영 여부 기록 |
| `확인 완료` | 검수 기준을 충족함 | 추가 조치 없음 |

검수 의견은 가능한 한 다음 형식으로 기록한다.

```markdown
| 등급 | 위치 | 내용 | 근거 | 담당 | 처리 상태 |
|---|---|---|---|---|---|
| 필수 수정 | 6. 시간대 전환 규칙 | 전환 적용 시점이 FSM과 연결되지 않음 | 실행 순서 불명확 | 시스템 기획 | 미처리 |
```

`필수 수정` 또는 미해결 `논의 필요`가 있으면 검수 상태를 `[수정 필요]`로 변경한다.

## 8. 검수 완료 및 확정 기준

### 8.1 검수 완료 조건

다음 조건을 모두 만족하면 검수 상태를 `[검수 완료]`로 변경할 수 있다.

- 필수 수정 사항이 모두 해결됐다.
- 다른 기준 문서와의 충돌이 해결됐다.
- 구현 또는 제작에 필요한 규칙이 검수 범위 안에서 충분히 정의됐다.
- 남은 미정 항목이 검수 범위와 분리돼 있다.
- 책임자와 검수자가 검수 완료 사실을 확인했다.

### 8.2 확정 조건

다음 중 하나에 해당하면 `[확정]`으로 변경할 수 있다.

- 회의 결정이 필요한 모든 항목이 결정됐다.
- 프로젝트 책임자가 최종 기준으로 지정했다.
- 검수 완료된 내용이 메인 GDD에 반영되고 기준 문서가 명시됐다.

확정 시 결정 상태를 `[확정]`으로 변경하고 문서를 `제안/`에서 대응하는 `확정/` 하위 폴더로 이동한다.

검수 완료 또는 확정 시 다음 내용을 변경 기록에 남긴다.

- 검수 완료·확정 일자
- 검수자와 확정한 사람 또는 회의
- 검수·확정 범위
- 제외된 `[작성 필요]` 및 `[논의 필요]` 항목

## 9. 변경 관리

### 9.1 확정 전 변경

- 초안 단계에서는 문서 본문을 직접 수정한다.
- 검수 중에는 검수 의견의 처리 여부가 추적되도록 변경한다.
- 큰 방향 변경이 발생하면 기존 검수 결과를 그대로 재사용하지 않고 재검수한다.

### 9.2 확정 후 변경

확정된 규칙을 변경할 때는 다음 정보를 먼저 기록한다.

```markdown
## 변경 요청

- 변경 대상:
- 변경 이유:
- 기존 규칙:
- 변경 규칙:
- 영향받는 시스템:
- 영향받는 문서:
- 재검수 대상:
- 결정 상태: [논의 필요]
```

- 확정 내용을 예고 없이 덮어쓰지 않는다.
- 변경으로 영향을 받는 문서를 함께 갱신한다.
- 구현 중인 기능에 영향이 있으면 담당 팀에 공유한 뒤 반영한다.
- 핵심 규칙 변경은 최소한 구조·규칙·제작 검수를 다시 진행한다.

## 10. 파일명 및 문서 구조

### 10.1 폴더 구조

프로젝트 문서는 다음 폴더에 분류해 저장한다.

```text
Waredo 2.0/
├─ 제안/
│  ├─ GDD/       검토 중인 프로젝트 전체 GDD와 통합 기획서
│  ├─ 시스템/    검토 중인 개별 시스템 기획서
│  ├─ 콘텐츠/    검토 중인 콘텐츠 기획서
│  └─ 문서관리/  검토 중인 작성·검수·운영 문서
└─ 확정/
   ├─ GDD/       확정된 프로젝트 공식 GDD
   ├─ 시스템/    확정된 개별 시스템 기획서
   ├─ 콘텐츠/    확정된 콘텐츠 기획서
   └─ 문서관리/  확정된 작성·검수·운영 문서
```

분류 기준은 다음과 같다.

- 여러 시스템의 상위 기준을 정의하면 `GDD`에 저장한다.
- 하나의 기능이나 규칙 체계를 정의하면 `시스템`에 저장한다.
- 시스템 규칙을 이용해 제작하는 플레이 대상과 수량을 정의하면 `콘텐츠`에 저장한다.
- 문서를 작성·검수·관리하기 위한 자료는 `문서관리`에 저장한다.
- 결정 상태가 `[제안]`이면 `제안/`, `[확정]`이면 `확정/` 아래에 저장한다.
- 두 분류에 걸치는 문서는 실제 원본 역할을 기준으로 한 곳에만 저장하고 다른 문서에서 참조한다.
- 문서에서 다른 문서를 지정할 때는 현재 문서 위치를 기준으로 한 상대경로를 사용한다.
- 프로젝트 루트에는 분류되지 않은 문서를 두지 않는다.

### 10.2 파일명

파일명은 내용을 바로 식별할 수 있도록 작성한다.

```text
Waredo_2.0_GDD_[시스템명].md
Waredo_2.0_[분야]_[문서명].md
```

예시:

```text
확정/시스템/Waredo_2.0_시간대_전환_시스템_기획서.md
제안/문서관리/Waredo_2.0_문서_관리_및_검수_규칙.md
```

- `최종`, `진짜최종`, `수정본` 같은 표현을 파일명에 사용하지 않는다.
- 버전 구분은 Git 이력, 결정 상태 및 검수 상태로 관리한다.

### 10.3 권장 문서 구성

시스템 기획 문서는 가능한 범위에서 다음 순서를 사용한다.

1. 시스템 개요 및 목적
2. 핵심 플레이 또는 사용자 흐름
3. 용어 정의
4. 진입·실행·종료 규칙
5. 변수 및 데이터
6. 다른 시스템과의 연결
7. 예외 및 실패 처리
8. UI·연출 요구사항
9. 개발 우선순위와 고도화 범위
10. 작성·논의 필요 목록
11. 검수 결과 및 변경 기록

## 11. Git 관리 규칙

### 11.1 스테이징

- 하나의 작업 목적과 관련된 문서만 함께 스테이징한다.
- 다른 사람이 만든 미추적 파일이나 관련 없는 변경은 임의로 포함하지 않는다.
- 스테이징 전 `git diff --check`로 기본 형식 오류를 확인한다.

### 11.2 커밋

- 커밋 하나에는 설명 가능한 하나의 변경 목적만 담는다.
- 초안 저장, 검수 반영, 확정 반영을 가능한 한 구분한다.
- 커밋 메시지는 변경 결과를 구체적으로 작성한다.

권장 형식:

```text
docs: 시간대 전환 시스템 초안 추가
docs: 시간대 전환 시스템 검수 의견 반영
docs: 확정된 시간대 전환 규칙 GDD 반영
```

### 11.3 푸시 및 공유

- 커밋 전 결정 상태, 검수 상태와 스테이징 범위를 다시 확인한다.
- 검수 요청 문서는 커밋 또는 공유 후 검수자에게 대상 파일과 검수 범위를 알린다.
- 확정되지 않은 문서는 구현 기준으로 오해되지 않도록 `[제안]` 상태를 명시한다.
- 원격 저장소에 올렸거나 검수를 완료했다는 사실만으로 문서가 확정된 것으로 간주하지 않는다.

## 12. 정기 문서 점검

다음 시점에 관련 문서를 점검한다.

- 핵심 시스템 규칙이 변경됐을 때
- 구현 과정에서 문서와 실제 동작이 달라졌을 때
- 프로토타입 또는 플레이테스트 결과가 나왔을 때
- 콘텐츠 제작을 시작하기 전
- 마일스톤 또는 챕터 제작을 완료했을 때

정기 점검에서는 다음을 확인한다.

- 더 이상 유효하지 않은 규칙
- 구현과 불일치하는 내용
- 해결되지 않은 `[작성 필요]`와 `[논의 필요]`
- 중복되거나 서로 충돌하는 문서
- 검수를 완료했지만 확정 또는 메인 GDD 반영이 끝나지 않은 내용
- 폐기 또는 보관 상태로 전환해야 하는 문서

## 13. 최소 운영안

초기에는 다음 네 가지 규칙만 반드시 적용한다.

1. 모든 문서 상단에 `결정 상태`, `검수 상태`, `책임자`, `최근 수정일`, `기준 문서`를 표시한다.
2. 문서는 `[제안]` 폴더에서 `[초안] → [검수 요청] → [수정 필요 또는 검수 완료]` 순서로 검수한다.
3. 검수는 `구조 → 규칙 → 플레이 → 제작` 순서로 진행하고 필수 수정 사항을 기록한다.
4. 최종 결정된 문서만 `[확정]`으로 바꾸고 `확정/` 폴더로 이동한다. 확정 문서 변경은 변경 이유와 영향 범위를 남긴 뒤 재검수한다.

이 최소 운영안이 안정적으로 사용된 이후 검수자 지정, 변경 요청 양식, 정기 점검 주기 등을 팀 상황에 맞춰 확장한다.
