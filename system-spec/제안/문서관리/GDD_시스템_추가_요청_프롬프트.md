# GDD 시스템 추가 요청 프롬프트

> 결정 상태: `[제안]` · 검수 상태: `[초안]`

기존 GDD에 새로운 시스템을 추가하거나 기존 시스템을 확장할 때 아래 규칙에 따라 문서를 갱신해줘.

이 작업의 목적은 사용자가 제공한 내용을 기존 시스템 구조에 정확히 편입하고, 시스템 및 변수 사이의 연결 관계와 모순을 확인하는 것이다.

---

## 1. 최우선 규칙

### 1.1 자의적인 추가 금지

- 사용자가 제공하지 않은 기능, 규칙, 수치, 콘텐츠, 조건, 예외, 보상, 연출을 임의로 추가하지 마.
- 일반적인 게임 사례나 다른 게임의 구조를 근거로 내용을 확정하지 마.
- 기존 문서에 없는 내용을 자연스러운 사실처럼 보완하지 마.
- 입력 정보가 부족한 항목은 추측하지 말고 `[작성 필요]`로 표시해.
- 여러 방향 중 결정이 필요한 항목은 `[논의 필요]`로 표시해.
- 사용자가 명시한 내용은 의미를 바꾸거나 축소하지 말고 그대로 반영해.
- 문장을 정리하기 위한 표현 수정은 가능하지만 새로운 기획 의도가 추가되면 안 돼.

### 1.2 기존 GDD 우선 확인

- 시스템을 추가하기 전에 기존 GDD 전체에서 같은 시스템, 유사한 기능, 같은 변수, 같은 용어가 이미 존재하는지 확인해.
- 같은 기능이 존재하면 중복 시스템을 만들지 말고 기존 시스템과의 통합 또는 분리 필요성을 표시해.
- 기존에 확정된 `[유지]`, `[변경]`, `[고도화]` 내용과 충돌하지 않는지 확인해.
- 기존 시스템의 상위·하위·상호 관계 및 확정 순서를 확인한 뒤 추가 위치를 정해.

---

## 2. 입력 정보

아래 내용을 기준으로 작업해.

### 2.1 기존 GDD

```text
[기존 GDD 전문 또는 파일 위치]
```

### 2.2 추가할 시스템

- 시스템명: [작성 필요]
- 추가 목적: [작성 필요]
- 유지 / 변경 / 신규 / 고도화 구분: [작성 필요]
- 시스템 상세: [작성 필요]
- 사용자가 명시한 변수: [작성 필요]
- 사용자가 명시한 연결 시스템: [작성 필요]
- 아직 결정되지 않은 내용: [작성 필요]

---

## 3. 시스템 구조 분석

추가할 시스템이 기존 구조에서 어디에 위치하는지 분석하고 다음 표에 반영해.

| 항목 | 작성 내용 |
|---|---|
| 시스템명 | 사용자가 제공한 명칭 |
| 구분 | `[유지]` / `[변경]` / `[신규]` / `[고도화]` |
| 계층 구분 | 상위 / 하위 / 상호 |
| 직속 상위 시스템 | 이 시스템의 규칙과 성립 조건을 정의하는 시스템 |
| 직속 하위 시스템 | 이 시스템의 규칙에 종속되는 시스템 |
| 상호 연관 시스템 | 서로 값을 주고받지만 직접 종속되지 않는 시스템 |
| 확정 순서 | 먼저 확정되어야 하는 시스템을 기준으로 한 순서 |
| 추가 근거 | 사용자가 제공한 내용 또는 기존 GDD의 근거 |

계층 및 연결 관계는 반드시 기존 GDD의 시스템 의존성 표와 도식에도 동일하게 반영해. 표와 본문, 도식의 연결 방향이 서로 달라지면 안 돼.

---

## 4. 변수 관리

추가되는 시스템에서 사용하는 모든 변수를 확인하고 변수 간 연결성을 명시해.

### 4.1 변수별 필수 작성 항목

| 항목 | 설명 |
|---|---|
| 변수명 | 실제 명칭. 미정이면 `[작성 필요]` |
| 의미 | 변수가 나타내는 값 또는 상태 |
| 정의 위치 | 변수를 최초 정의하는 시스템 |
| 소속 시스템 | 변수의 최종 소유권과 수정 권한을 가진 시스템 |
| 값을 생성·변경하는 시스템 | 해당 값을 생성하거나 변경하는 주체 |
| 값을 활용하는 시스템 | 해당 값을 읽거나 조건 판단에 사용하는 시스템 |
| 연결 변수 | 직접 영향을 주거나 받는 다른 변수 |
| 연결 방향 | `A → B` 또는 `A ↔ B` |
| 갱신 시점 | 값이 변경되는 시점. 미정이면 `[작성 필요]` |
| 저장 여부 | 저장/비저장 여부. 미정이면 `[작성 필요]` |
| 충돌 가능성 | 기존 변수와 의미·소유권·갱신 시점이 겹치는지 여부 |

### 4.2 변수 연결성 규칙

- 같은 의미의 변수를 여러 시스템에서 중복 정의하지 마.
- 변수는 하나의 소속 시스템에서만 원본 값을 소유하도록 정리해.
- 다른 시스템은 원본 변수를 참조하거나 정해진 요청을 통해 변경하도록 표시해.
- 어떤 변수가 다른 변수의 조건·결과·계산 근거로 사용되면 연결 방향을 반드시 적어.
- 순환 연결이 발견되면 `A ↔ B`로 단순 처리하지 말고, 실제로 누가 먼저 값을 정의하고 누가 결과를 반영하는지 확인해.
- 입력 정보만으로 연결 방향을 확정할 수 없으면 `[논의 필요]`로 표시해.
- 변수의 자료형, 기본값, 최솟값, 최댓값, 단위가 제공되지 않았다면 임의로 채우지 말고 `[작성 필요]`로 남겨.

### 4.3 변수 연결 도식

변수 연결은 다음 형식으로 요약해.

```text
[정의 시스템] 변수 A → [활용 시스템] 변수 B
[정의 시스템] 변수 B → {[활용 시스템 1], [활용 시스템 2]}
```

연결 방향의 근거가 없는 경우:

```text
[논의 필요] 변수 A와 변수 B의 갱신 주체 및 연결 방향
```

## 5. 시스템 간 연결점 확인

추가 시스템이 기존 시스템과 만나는 지점을 빠짐없이 확인해.

| 연결 대상 | 확인 내용 |
|---|---|
| 전투 흐름 | 진입, 실행, 종료, 정산 시점에 영향을 주는가 |
| 턴 및 FSM | 턴 순서, 상태, 행동 가능 여부, 전이 조건에 영향을 주는가 |
| 캐릭터 | 파라미터, 타입, 보유 상태, 행동에 영향을 주는가 |
| 스킬·상태이상·유물 | 적용 조건, 효과, 중첩, 해제에 영향을 주는가 |
| 전투판·환경 요소 | 위치, 이동, 타일, 환경 상태에 영향을 주는가 |
| 아웃게임·대화 시나리오 | 진행 정보, 보유 정보, 발생 조건에 영향을 주는가 |
| UI·애니메이션·연출 | 입력, 표시 정보, 재생 조건에 영향을 주는가 |

연결되지 않는 항목을 억지로 연결하지 마. 실제 연결 근거가 있을 때만 기록하고, 가능성만 있는 경우 `[논의 필요]`로 표시해.

## 6. 모순 및 충돌 검증

시스템 추가 후 다음 항목을 반드시 검증해.

1. **계층 역전:** 하위 시스템이 상위 시스템의 핵심 규칙을 임의로 결정하고 있지 않은가.
2. **순환 의존:** A가 B에 종속되고 B가 다시 A에 종속되는 구조가 생기지 않았는가.
3. **변수 소유권 충돌:** 같은 변수를 둘 이상의 시스템이 원본으로 정의하거나 수정하지 않는가.
4. **갱신 순서 충돌:** 변수를 읽는 시점과 변경하는 시점이 뒤바뀌지 않는가.
5. **용어 충돌:** 같은 용어가 시스템마다 다른 의미로 사용되지 않는가.
6. **유지·변경 충돌:** `[유지]` 항목의 실제 내용이 추가 시스템으로 인해 변경되지 않는가.
7. **본문·표·도식 불일치:** 시스템 관계와 변수 연결 방향이 모든 위치에서 동일한가.
8. **중복 기능:** 기존 시스템과 같은 책임을 가진 기능이 새로 만들어지지 않았는가.
9. **확정 순서 충돌:** 먼저 확정되어야 할 상위 시스템보다 하위 시스템이 앞서 확정되도록 작성되지 않았는가.
10. **팀별 착수 조건 충돌:** 선행 시스템이 미정인데 하위 제작 작업이 착수 가능으로 표시되지 않았는가.

모순이 발견되면 임의로 수정하지 말고 아래 형식으로 문서 마지막에 기록해.

| 항목 | 위치 | 모순 유형 | 근거 | 영향받는 시스템·변수 | 필요한 결정 |
|---|---|---|---|---|---|
| [모순 내용] | [본문/표/도식 위치] | [유형] | [근거] | [대상] | `[논의 필요]` |

모순이 없으면 `현재 입력 범위에서 발견된 모순 없음`이라고 적어.

## 7. 팀별 제작 내용 반영

추가 시스템으로 인해 발생하는 작업을 기존 팀별 제작 내용 표에 반영해.

| 팀 | 해당 시스템·항목 | 제작 내용 | 상태 | 우선순위 | 착수 조건 |
|---|---|---|---|---|---|
| [작성 필요] | [시스템명] | [사용자가 제공한 범위 또는 작성 필요] | [유지/변경/신규/고도화] | [작성 필요] | [선행 시스템 또는 작성 필요] |

- 사용자가 말하지 않은 제작 파트나 산출물을 임의로 추가하지 마.
- 시스템의 확정 순서와 팀의 착수 조건을 일치시켜.
- 콘텐츠 제작은 관련 시스템의 규칙과 변수가 확정·검증된 뒤에 배치해.
- 새 시스템으로 기존 팀의 작업 범위가 변하면 해당 행도 함께 갱신해.

---

## 8. 문서 반영 규칙

추가 시스템을 다음 위치에 모두 반영해.

1. 유지 / 변경 / 신규 / 고도화 목록
2. 시스템 분류 및 의존성 표
3. 시스템 의존성 도식
4. 변수 관리 표와 변수 연결 도식
5. 확정 순서
6. 시스템별 상세
7. 개발 우선순위 및 검증 순서
8. 팀별 제작 내용과 착수 흐름
9. MVP 범위에 미치는 영향
10. 모순 검증 결과

한 위치에만 시스템을 추가하고 다른 표나 도식을 누락하지 마.

## 9. 시스템별 상세 작성 형식

```markdown
### [시스템명] [구분]

- 시스템 목적: [사용자 입력 또는 작성 필요]
- 계층 구분: [상위/하위/상호]
- 직속 상위 시스템: [시스템명]
- 직속 하위 시스템: [시스템명 또는 없음]
- 상호 연관 시스템: [시스템명 또는 없음]
- 진입 조건: [작성 필요]
- 실행 규칙: [작성 필요]
- 종료 조건: [작성 필요]
- 정의 변수: [작성 필요]
- 활용 변수: [작성 필요]
- 다른 시스템에 제공하는 값: [작성 필요]
- 다른 시스템에서 받는 값: [작성 필요]
- 예외 처리: [작성 필요]
- 확정 순서: [번호]
- 팀별 제작 내용: [작성 필요]
```

## 10. 최종 출력 순서

1. 추가 요청 요약
2. 시스템 계층 및 의존성 반영 결과
3. 변수 정의·소유·활용·연결 관계
4. 시스템별 상세
5. 기존 시스템에 미치는 영향
6. 확정 순서 및 개발 우선순위 변경
7. 팀별 제작 내용 변경
8. `[작성 필요]` 목록
9. `[논의 필요]` 목록
10. 모순 검증 결과

최종 출력 전에 사용자가 제공하지 않은 내용이 확정형 문장으로 추가되지 않았는지 다시 검사해.
