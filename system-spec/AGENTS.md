# Waredo 2.0 에이전트 운영 규칙

이 저장소는 Waredo 2.0의 게임 기획 문서와 전투 프로토타입을 관리한다. 모든 에이전트는 이 파일과 자신에게 지정된 `프롬프트/ainus-*.md`를 함께 따른다.

## 작업 시작 시 읽을 기준

1. 모든 작업은 `인수인계/CURRENT.md`를 먼저 읽고, 현재 목표·완료 상태·다음 작업·주의사항을 복원한다.
2. `CURRENT.md`와 Git 실제 상태가 다르면 `git status`, 최근 커밋, 관련 파일을 기준으로 차이를 확인하고 사용자에게 알린다.
3. 기획·문서 작업은 `확정/Waredo_2.0_전체_기획_관리.md`를 읽는다.
4. 대상 시스템과 연결된 `확정/` 문서를 단일 원본으로 취급한다.
5. `제안/`은 검토 중인 안, `보류/`는 적용 제외, `레거시/`는 참고 자료다. 사용자가 명시하지 않으면 이 문서들을 현재 규칙처럼 적용하지 않는다.
6. 문서 작성·검수 작업은 `제안/문서관리/Waredo_2.0_문서_관리_및_검수_규칙.md`도 읽는다. 이 규칙 자체가 `[제안]` 상태임을 결과에 명시한다.
7. 프로토타입 작업은 `도구/전투 프로토타입/README.md`와 해당 폴더의 `package.json`을 먼저 읽는다.

## 역할별 에이전트

역할을 맡은 에이전트는 아래 파일을 처음부터 끝까지 읽은 뒤 작업한다. 원본 프롬프트에 현재 환경에 없는 전용 스킬이나 명령이 나오면 기능을 지어내지 말고, 사용 가능한 읽기·검색·실행 도구로 같은 목적을 달성하거나 제약을 보고한다.

| 역할 | 프롬프트 | 호출 조건 |
|---|---|---|
| 인수인계 기록관 | `프롬프트/ainus-handoff-recorder.md` | 작업 대화를 분석해 다른 로컬에서 이어갈 수 있는 기록을 만들거나 갱신할 때 |
| 기획 오케스트레이터 | `프롬프트/ainus-planner.md` | 여러 기획 단계를 조율하고 최종 산출물을 취합할 때 |
| 비개발자 기획 리드 | `프롬프트/ainus-planning-lead.md` | 아이디어부터 GDD 초안까지 단계별로 안내할 때 |
| 게임 디자이너 | `프롬프트/ainus-game-designer.md` | 코어 루프, 메커니즘, 밸런스, 진행 곡선을 설계할 때 |
| 내러티브 디자이너 | `프롬프트/ainus-narrative-designer.md` | 세계관, 캐릭터, 대사, 분기 구조를 설계할 때 |
| 리서처 | `프롬프트/ainus-research.md` | 게임·장르·시장 레퍼런스를 조사할 때 |
| 분석가 | `프롬프트/ainus-analyst.md` | 시장·도메인·기술 조사를 정규화할 때 |
| 설계 검토관 | `프롬프트/ainus-architect.md` | 구현 전에 계약, 의존성, 준비도를 점검할 때 |
| 게임 기획 QA | `프롬프트/ainus-game-qa.md` | 재미, 페이싱, 지배 전략, 죽은 선택지를 평가할 때 |
| 게임 문서 품질 점검 | `프롬프트/ainus-game-quality.md` | GDD의 누락, 모순, 경계값, 참조 오류를 검수할 때 |
| 주입 준비도 검수 | `프롬프트/ainus-injection-readiness.md` | Unity용 데이터와 참조의 완결성을 검수할 때 |
| 독립 검수관 | `프롬프트/ainus-reviewer.md` | 코드·문서 결과를 작업자와 분리해 최종 검수할 때 |

## 에이전트 호출 규칙

- 하나의 단순 수정은 주 에이전트가 직접 처리한다.
- 독립적으로 나눌 수 있는 조사·설계·검수 작업만 역할 에이전트에 맡긴다.
- 각 에이전트에게 대상 파일, 질문, 산출물 형식, 수정 가능 여부를 명시한다.
- 에이전트는 지정 범위를 벗어난 파일을 수정하지 않는다. 기본은 읽기 전용이며, 주 에이전트가 명시한 경우에만 파일을 편집한다.
- 서로 독립된 조사나 검수는 병렬로 수행할 수 있다. 같은 파일을 수정하는 작업과 선행 결과가 필요한 작업은 순차로 수행한다.
- 작성자와 최종 검수자는 분리한다. 검수 에이전트에게 작성 에이전트의 결론을 정답처럼 주입하지 않는다.
- 주 에이전트는 에이전트 결과를 그대로 붙이지 않고 기준 문서와 대조해 충돌·중복·근거 수준을 확인한 뒤 통합한다.
- 에이전트가 낸 설계안이나 PASS 판정은 사용자 승인이나 문서의 `[확정]` 상태를 대신하지 않는다.

## 인수인계 기록 규칙

- 의미 있는 파일 변경, 설계 결정, 검수 결과 또는 다음 작업이 생기면 최종 응답 전에 인수인계 기록관을 사용해 `인수인계/CURRENT.md`를 갱신한다.
- 장기 보존 가치가 있는 작업 단위가 끝나면 `인수인계/기록/YYYY-MM-DD_작업명.md`에 스냅샷을 추가한다. 같은 작업을 조금 수정한 정도라면 새 기록을 남발하지 않고 기존 당일 기록을 갱신한다.
- 기록에는 대화 전문이나 내부 추론을 넣지 않는다. 목표, 사용자 결정, 결정 근거, 완료한 일, 변경 파일, 검증 결과, 미완료 작업, 다음 행동, Git 상태만 요약한다.
- 비밀번호, 토큰, 개인 연락처, 로컬 전용 비밀 경로 등 민감한 정보는 기록하지 않는다.
- 추측은 사실처럼 기록하지 않는다. 사용자 결정은 `결정`, 에이전트 제안은 `제안`, 미확정 내용은 `미결정`으로 구분한다.
- `작업 시작` 요청을 받으면 원격 변경을 가져온 뒤 `CURRENT.md`와 최신 기록을 읽고 복원된 상태를 짧게 보고한다.
- `작업 기록` 요청을 받으면 현재 대화와 Git 상태를 분석해 인수인계 문서만 갱신한다.
- `작업 마무리`, `GitHub에 올려`, `푸시` 요청을 받으면 작업 변경과 인수인계 문서를 함께 검증하고 커밋·푸시한다. 관련 없는 변경은 포함하지 않는다.
- 푸시하지 않은 인수인계 변경이 있으면 최종 응답에서 다른 로컬에는 아직 전달되지 않았다고 명시한다.

## 문서 변경 규칙

- 사용자가 명시적으로 승인하지 않으면 `확정/` 문서를 제안 내용으로 덮어쓰지 않는다.
- 새 기획은 원칙적으로 `제안/`의 알맞은 하위 폴더에 생성하고 상단에 결정 상태와 검수 상태를 표시한다.
- 문서를 생성·이동·확정·폐기하면 같은 작업에서 `확정/Waredo_2.0_전체_기획_관리.md`의 상태와 경로를 갱신한다.
- 동일 규칙을 여러 문서에 원문처럼 중복 작성하지 않는다. 다른 문서에서는 단일 원본의 상대경로와 항목을 참조한다.
- 사용자에게서 정해지지 않은 수치나 규칙은 임의로 확정하지 않고 `[작성 필요]`, `[논의 필요]` 또는 설계 가정으로 표시한다.
- `제안/`에서 `확정/`으로의 이동과 결정 상태 `[확정]` 변경은 사용자 또는 명시된 책임자의 승인 없이는 수행하지 않는다.

## 검증과 완료 조건

- 문서 작업은 상태 표기, 상대경로, 용어, 단일 원본, 관련 시스템 충돌을 확인한다.
- 프로토타입 코드 작업은 가능한 범위에서 관련 테스트·빌드·린트를 실행하고 실제 실행 결과를 보고한다.
- 변경 후 `git diff --check`를 실행한다.
- 관련 없는 사용자 변경과 미추적 파일은 수정·삭제·스테이징하지 않는다.
- 완료 보고에는 변경 파일, 검증 결과, 남은 `[작성 필요]`·`[논의 필요]`, 사용자 결정이 필요한 항목을 포함한다.
- 완료 보고에는 인수인계 기록을 갱신했는지와 GitHub 동기화 여부도 포함한다.

## 기본 언어

- 사용자 응답과 기획 문서는 특별한 요청이 없으면 한국어로 작성한다.
- 코드 식별자, 파일명, 기존 영문 용어는 불필요하게 번역하거나 이름을 바꾸지 않는다.
