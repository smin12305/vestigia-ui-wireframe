# VESTIGIA — 인게임_전투 화면 비교·누락 분석

분석일: 2026-09-23. **Figma 편집 없음.** 사용자가 직접 수정할 때 참고할 작업 목록이다.

## 1. 가장 먼저 볼 결론

현재 화면은 **전투 HUD 배치와 캐릭터 정보 열람의 골격**이 있다. 가장 큰 공백은 `아군 선택 → 이동 경로 작성 → 공격/스킬 지정 → 행동 확정 → 전체 계획 확인 → 미래 관측/작전 개시 → 결과 → 다음 계획`의 중간 상태다.

새 UI를 전부 다시 설계할 필요는 없다. 기존 메인 화면을 바탕으로 아래 6개 묶음을 우선 보강하면 한 턴을 끝까지 검증할 수 있다.

1. 이동 경로 작성·수정 상태
2. 공격/스킬 타겟팅·확정·취소 상태
3. 전체 계획 완료와 적 행동 예고
4. 미래 관측 중·관측 종료·계획 복귀
5. 실제 실행 중·행동 결과·다음 턴
6. 과거/미래 진입 후·잔여 1턴·현재 복귀

여기서 ‘묶음’은 새로운 전체 화면 1개를 뜻하지 않는다. 같은 HUD 안의 보드 표시, 버튼 상태, 오버레이 변형으로 충분한 경우가 많다. 모든 Hover나 연출 프레임을 만들기보다 플레이어가 다른 판단을 내려야 하는 상태를 만든다.

## 2. 확인 범위와 근거의 한계

- Figma [인게임_전투](https://www.figma.com/design/EnCDeN7hohOA5p8rE2rsNA?node-id=0-1)의 최상위 주요 화면 12개를 각각 렌더 이미지로 확인하고, 레이어·텍스트·숨김 레이어·프로토타입 연결·컴포넌트 상태를 조회했다. `폐기` 프레임과 종이 스케치는 현재 구현된 흐름에 포함하지 않았다.
- ‘없음’은 **이 페이지의 현재 화면·레이어·연결에서 확인되지 않음**을 뜻한다. 다른 페이지나 별도 파일까지 없다고 판정한 것은 아니다.
- 기획서는 기존 `system-spec/` 사본을 재사용했다. 로컬 변경은 없었고, 원격 HEAD와 로컬 HEAD가 `0f3b23f59ea51f294a9c1db636d80b5abe4b2c44`로 일치함을 `git ls-remote`로 확인했다.
- 첨부 HTML은 UI 템플릿, 입력 처리, 계획·실행·시뮬레이션 코드를 정적으로 읽었다. 브라우저가 로컬 파일 URL을 보안 정책으로 차단하여 **직접 플레이·애니메이션·실행 결과는 검증하지 못했다.** 아래 ‘HTML에 있음’은 코드 존재를 뜻한다.
- 기준은 현행 시스템 본문과 후속 결정이다. HTML의 구현이나 저장소 안의 과거 작업 지시를 새로운 기획 승인으로 간주하지 않았다.
- 저장소의 상태 표기가 일부 어긋난다. 상태이상·환경요소 문서 상단에는 `[제안]`이 남아 있지만, [전체 기획 관리](../system-spec/확정/Waredo_2.0_전체_기획_관리.md)는 확정 승격 이력을 명시한다. 핵심 전투 규칙은 현행 기준으로 비교하되 개별 미정·레벨 배치·종료 후 정산은 자동 확정하지 않았다. `[임시]전투 시뮬레이션` 표기도 유지한다.

## 5. 추가 상태 작업 목록 — 우선순위 순

P0는 한 턴의 핵심 판단과 입력을 검증하는 데 필요하다. P1은 실제 플레이에서 이유를 이해하거나 다음 단계로 넘어가기 위해 필요하다. 제안하는 UI 방식은 시스템 규칙 자체와 구별한다.

### P0-A. 이동 경로 작성·수정

**현재:** 아군 선택 링만 있다. **근거:** 전투 4-1-4~5, HTML `beginMoveDrag`, `continueMoveDrag`, `setPath`.

- 추가할 상태: `이동 가능 범위 표시` → `경로 작성 중` → `도착 위치가 지정된 상태`.
- 표시: 선택 캐릭터, 현재 위치, 도착 예상 위치, 경로 선/화살표, 사용 이동력/최대 이동력. 도착 예상 캐릭터는 실제 위치와 구별한다.
- 입력 제안: 캐릭터/경로에서 드래그해 경로 작성, 기존 경로로 되짚으면 뒤쪽 경로 단축. HTML에 대응 코드가 있다.
- 예외: 이동력 초과·판 밖·유효하지 않은 경로를 거절했음을 표시. 실제 실행 중 다른 캐릭터와 충돌해 정지하는 결과는 별도로 표현한다.
- 완료 조건: 이동 없이 공격하기, 이동만 하기, 경로 수정 후 공격하기가 서로 구별된다. 이동력이 변경되면 경로 전체가 지워지고 재지정 안내가 나와야 한다.

### P0-B. 공격/스킬 타겟팅과 확정·취소

**현재:** 버튼·활성 변형은 있지만 타겟팅 화면과 확정 UI가 없다. **근거:** 전투 4-1-4, 4-1-6~7; 캐릭터 4-1-5~6; HTML `isTargetable`, `confirm-action`, `cancel-action`.

| 필요한 대표 상태 | 화면에서 보여줄 차이 | 확정/취소 |
|---|---|---|
| 방향성 공격 | 이동 도착점 기준 상하좌우 방향과 실제 영향 범위 | 방향 선택 후 확정, 취소하면 이동 편집으로 복귀 |
| 타일 선택형 | 선택 가능 타일 범위와 선택한 목표 주변 영향 범위를 구별 | 목표 타일 지정 후 확정. 목표가 없는 상태에서는 확정 불가 |
| 자기 기준형 | 도착 위치 중심 패턴과 영향받는 대상 | 별도 적을 고르게 하지 않음. 필요하면 범위 확인 후 확정 |
| 자가 버프형 | 자신에게 적용됨, 반격이라면 반격 발동 범위 표시 | 자기 재선택 또는 행동 확정으로 완료 |
| 회복형 예시 | 아군 대상·예상 회복·회복 범위를 피해 표시와 구별 | 야나의 회복을 대표 샘플로 재사용 가능 |

- 하단에 선택한 행동명, 효과, `확정`·`취소`를 보인다. “캐릭터 행동 확정”과 전체 턴의 “작전 개시”를 다른 수준의 입력으로 구별한다.
- 쿨타임 0/남음과 대상 미지정 상태를 구별한다. 기존 스킬 버튼 3종에 이유와 남은 턴을 붙이면 된다.
- 일반 공격과 스킬은 한 캐릭터의 같은 행동에 동시 선택할 수 없다. 새 모드를 선택했을 때 기존 주 행동이 교체됨을 표현한다.
- 타일 선택형 목표는 이동 도착점 기준 상대 위치다. 다른 실제 위치에서 실행될 때 목표도 달라질 수 있으므로, 보드 위 원점과 범위를 함께 보여준다.
- 취소 시 이동 계획을 유지하고 주 행동만 해제하는 방식은 HTML `planNone`과 일치하는 UX 제안이다. 모든 계획 초기화와 혼동하지 않게 한다.

### P0-C. 전체 계획 확인과 적 행동 예고

**현재:** 순서 초상화는 있으나 누가 무엇을 할지, 누가 설정을 끝냈는지 확인하기 어렵다. 적 정보 열람은 행동 예고를 대신하지 못한다. **근거:** 전투 브리핑·4-1-1·4-1-4, HTML `getEnemyThreatPredictions`, `planned`, `drawPlannedActionLabels`.

- 기존 메인에 `미설정/이동만/공격/스킬/확정` 상태를 작은 배지나 요약으로 추가한다.
- 적 선택 시 해당 적의 순번, 이동 경로, 도착 위치, 공격/스킬 종류, 방향/영향 범위를 강조한다. 다른 예고는 흐리게 해서 선이 겹쳐도 읽을 수 있게 한다.
- 전체 계획 보기에서는 아군·적군과 이동·피해·회복을 색 외에도 선 모양·아이콘으로 구별한다.
- 순서 변경 중에는 교환 가능한 아군 슬롯과 고정된 적 슬롯을 구분하고, 교환 후 행동 계획도 캐릭터와 함께 이동함을 보여준다.
- 빈 계획은 오류가 아니라 대기다. 전원이 공격을 지정해야만 작전 개시가 가능하도록 만들지 않는다. 다만 **선택은 했지만 목표를 아직 정하지 않은 행동**은 미완성으로 구별한다.
- 계획 초기화는 HTML 기준 아군 이동·주 행동을 지우며 순서와 적 계획은 유지한다. 제안 문구는 `아군 행동 계획을 초기화했습니다`. 순서까지 초기화하려면 별도 UX 결정을 해야 한다.

### P0-D. 미래 관측 중·종료·계획 복귀

**현재:** 버튼만 있다. **근거:** 전투 4-1-9 `[임시]전투 시뮬레이션`, HTML `createObservation`, `observeFuture`, `mn`.

- 추가할 상태: `미래 관측 중` → `예상 결과 확인` → `기존 계획 복귀`.
- 실제 실행과 구별되는 상시 표식이 필요하다. 시간대가 미래가 된 것처럼 보이게 하지 말고 `예측 중 · 실제 전투에 반영되지 않음`을 표시한다. 과거/미래 전환과 미래 관측은 다른 기능이다.
- 실행 순번, 예상 이동·HP·행동 실패·전투불능을 보여준다. 예상 승패에는 보상 획득이나 실제 다음 전투 버튼을 붙이지 않는다.
- 결과 화면은 큰 신규 페이지보다 종료 시 보드+작은 요약 오버레이로 충분하다. 결과를 살펴볼 시간을 주고 `계획으로 돌아가기`를 제공하는 것은 UX 제안이다. HTML은 관측 뒤 짧게 기다렸다 자동 복귀한다.
- 복귀 후 경로·순서·HP·쿨타임·파편·시간대·실제 턴은 관측 전 그대로여야 한다. 계획을 바꿨다면 이전 예상 결과를 최신처럼 표시하지 않는다.

### P0-E. 실제 실행과 다음 턴

**현재:** 작전 개시 이후 실제 전투 진행 화면이 없다. **근거:** 전투 4-1-1~2·4-1-8, HTML `executeTurn`, `.slot.executing`, 실행 단계 CSS.

- 추가할 상태: `행동 실행 중` → `개별 결과` → `다음 턴 계획`.
- 현재 행동 슬롯·캐릭터를 강조하고, 완료/예정/스킵을 구별한다. 계획 편집, 순서 변경, 시간대 변경 입력은 막는다.
- 최소 결과 예시는 일반 피해 1건, 상태이상으로 행동 스킵 1건, 충돌/범위 이탈로 실패 1건을 선택한다. 모든 스킬 연출을 만들 필요는 없다.
- 실패 시 “행동 취소”만 쓰지 말고 `범위 밖`, `기절로 행동 불가`, `충돌로 이동 종료`처럼 원인을 보여준다. 이미 이동한 위치까지 원상 복구된 것처럼 그리지 않는다.
- 같은 턴에서 죽거나 기절해 스킵된 슬롯을 없애 뒤의 번호를 당기지 않는다. 다음 턴에 새 슬롯 구성을 보여준다.
- 다음 턴에는 턴 번호 증가, 선공 교대, HP·쿨타임·상태 변화와 새로운 적 예고가 반영된다. `TURN 0` 플레이스홀더는 실제 샘플에서 1부터 사용한다.

### P0-F. 시간대 진입·체류·복귀와 계획 무효화

**현재:** 충전/선택 펼침 3장과 PAST 각성 정보는 있지만 전체 전투의 변화와 복귀가 없다. **근거:** 시간대 4-1~4·4-5, 전투 4-1-4-2.

| 상태 | 필수 정보와 전환 조건 |
|---|---|
| 현재·파편 부족 | `보유/최대` 수치, 전환 비용 100, 사용 불가 이유 |
| 현재·전환 가능 | 현재의 계획 단계이면서 파편 ≥100. 기존 펼침 화면 재사용 |
| 과거 진입 | 파편 100 차감, 아군 이동력 +1, 체류 2턴, 태그 일치 캐릭터 궁극기 |
| 미래 진입 | 파편 100 차감, 아군 일반 공격력 +3, 체류 2턴, 태그 일치 캐릭터 궁극기 |
| 체류 1턴 | `과거에서 1턴 남음` 등 지속 정보. 재전환 불가·파편 획득 없음 |
| 현재 복귀 | 두 번째 턴 종료 후 자동 복귀, 시간대 버프 해제·일반 스킬 복귀 |

- 시계 원형 게이지 외에 수치가 필요하다. 유물로 최대치가 130이면 `130/130 → 전환 → 30/130`도 표현 가능해야 한다. 최대 충전과 전환 가능은 같은 조건이 아니다.
- 시간대 변경은 버튼 입력 순간 적용된다. 행동 계획에 “나중에 시간대 전환”을 예약하는 화면으로 만들지 않는다.
- 이동력 증가·감소 시 해당 캐릭터의 이동 경로 전체 삭제. 활성 스킬이 달라지면 기존 스킬 계획 취소. 사용자에게 `이동력이 바뀌어 경로를 다시 지정하세요`, `활성 스킬 변경으로 스킬 계획이 해제되었습니다`를 보여준다.
- 시간대 전환 자체는 공유 쿨타임을 초기화하지 않는다. 별도 유물의 쿨타임 효과가 있으면 그 효과와 구별한다.

## 6. 기획서·HTML·Figma가 달라 그대로 복사하면 안 되는 점

| 항목 | 확인한 차이 | 이번 UI 설계 기준 |
|---|---|---|
| 최초 선공 | HTML `startBattle`/`tossFirstTeam`은 아군 고정. 전투 기획은 최초 50% 동전, 이후 교대 | 아군/적 선공 모두 수용하는 순서 표시. 동전 애니메이션 자체는 선택 사항 |
| 미래 보정 | HTML `getCriticalRate`에 미래 아군 +20이 있음. 현행 시간대 기획은 아군 일반 공격력 +3 | HTML 수치를 UI에 그대로 옮기지 말고 현행 문구 사용. 코드 전체 피해 계산의 정합성을 이번 UI 분석에서 보증하지 않음 |
| 타겟팅 분류 | HTML은 곡사를 방향 선택형 내부에서 상대 타일로 처리. 현행 기획은 `타일 선택형`을 별도로 명시 | 사용자에게는 실제 입력 방식에 맞춘 방향/타일/자기 기준/자가 버프 안내 |
| 미래 관측 진입 | HTML `Ee()`는 선택한 주 행동의 별도 확정을 요구. 기획은 현재까지 작성한 계획의 가상 재현 | 빈 계획의 대기와 목표 미지정을 구별. 별도 확정 조작은 UX 선택이며 모든 캐릭터 행동을 강제하지 않음 |
| 관측 결과 유지 | HTML은 가상 재생 후 자동 복귀 | 결과 확인 오버레이는 추가 UX 제안. 기획이 별도 정산 페이지를 요구하는 것은 아님 |
| 각성 샘플 | Figma 각성 정보는 야나 이미지로 보이며 PAST. 최신 야나 콘텐츠는 FUTURE | 야나의 실제 상태 예시라면 FUTURE로 수정. 범용 자리표시자라면 예시임을 명시 |
| 적 궁극기 | 적 정보창에도 `스킬 · 궁극기` 제목. 전투 기획의 프로토타입 기준 적은 시간대 태그·궁극기 없음 | 현재 적 데이터는 `스킬`로 구별. 미래 확장 설계를 확정된 현행 기능처럼 표시하지 않음 |
| 문서 상태 표기 | 일부 개별 문서의 제안 헤더와 전체 관리대장의 확정 안내 불일치 | 확정 승격 이력과 본문 후속 결정을 읽되, 미정 조건은 별도 표시. 저장소 원본은 이번에 수정하지 않음 |

## 7. 실제로 그릴 때의 최소 작업 순서

1. 메인 화면 하나를 작업 기준으로 정하고 아군 선택 진입·작전 개시 연결을 정리한다.
2. **야나 이동 → 자기 중심 회복 → 확정**으로 이동·범위·아군 대상·완료 배지를 한 번에 검증한다.
3. 방향성 공격 1개, 타일 선택형 1개, 자가 버프/반격 1개를 추가해 서로 다른 입력 방식을 채운다. 캐릭터마다 같은 상태를 반복 제작하지 않는다.
4. 적 예고와 전체 계획 확인을 추가하고, 순서 교환 뒤 계획이 캐릭터를 따라가는 모습을 만든다.
5. 같은 계획을 `미래 관측 → 복귀`와 `작전 개시 → 다음 턴` 두 경로로 연결한다.
6. 파편 100 도달 → 시간대 선택 → 2턴/1턴 → 현재 복귀를 추가한다. 이동/스킬 재지정 알림을 이 흐름에 넣는다.
7. 실제 승패, 제한 안내, 상태이상, 배치/유물/환경요소 순으로 확장한다.

각 상태 옆에는 `진입 조건 / 입력 / 바뀌는 정보 / 유지되는 정보 / 다음 상태`만 적으면 아트·개발 전달에 충분하다. 반복 버튼/리스트 내부 정렬은 필요할 때만 오토레이아웃을 적용하고, 보드와 HUD의 위치 판단은 현재 자유 배치를 유지해도 된다.

## 8. 검증 시나리오

- 경로만 그린 아군과 아무 계획 없는 아군을 함께 실행한다. 각각 이동만/대기로 처리되는지 확인한다.
- 공격 선택 후 취소한다. 이동 경로 유지와 주 행동 해제가 구별되는지 확인한다.
- 아군 순서를 교환한다. 적 슬롯은 고정이고 아군 계획은 캐릭터를 따라가는지 확인한다.
- 미래 관측에서 아군이 쓰러져도 복귀 후 실제 HP·파편·턴과 계획이 바뀌지 않는지 확인한다.
- 이동 계획 뒤 과거로 전환한다. 이동력 증가에 따라 경로가 지워지고 재지정 안내가 표시되는지 확인한다.
- 남은 쿨타임이 있는 상태에서 시간대를 바꾼다. 궁극기 표시가 생겨도 즉시 사용 가능한 것으로 오해되지 않는지 확인한다.
- 실행 중 기절/전투불능을 발생시킨다. 남은 슬롯 번호가 당겨지지 않고 스킵 이유가 보이는지 확인한다.
- 예상 승패와 실제 승패를 각각 확인한다. 예상 결과에서 실제 보상/진행이 발생하지 않는지 확인한다.
